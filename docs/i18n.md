# Internationalisation (i18n)

ORLOJ supports six locales: English (`en`), Czech (`cs`), German (`de`), French (`fr`), Spanish (`es`), and Chinese Simplified (`zh`). The implementation uses Next.js 16's native i18n routing — no third-party library.

## How it works

### Routing

All user-facing routes are prefixed with a locale segment:

| URL | Locale |
|---|---|
| `/en` | English (home) |
| `/cs/explore` | Czech (Explore) |
| `/de/profile` | German (Profile) |
| `/zh/register` | Chinese (Register) |

`proxy.ts` (Next.js 16's renamed middleware) intercepts every non-API, non-`_next` request. If the path has no locale prefix it reads `Accept-Language` and redirects:

```
/explore  →  /en/explore   (browser is English)
/profile  →  /de/profile   (browser is German)
/explore  →  /zh/explore   (browser is Chinese)
```

API routes at `app/api/` are not affected.

### Dictionary files

All user-visible strings live in six JSON files:

```
packages/app/dictionaries/en.json   ← English (source of truth)
packages/app/dictionaries/cs.json   ← Czech
packages/app/dictionaries/de.json   ← German
packages/app/dictionaries/fr.json   ← French
packages/app/dictionaries/es.json   ← Spanish
packages/app/dictionaries/zh.json   ← Chinese Simplified
```

Keys are organised by component namespace (`nav`, `auth`, `landing`, `explore`, `register`, `docs`, `launch`, `profile`, `shell`).

Interpolation uses `{placeholder}` syntax:

```json
"sentLinkTo": "We sent a sign-in link to {email}. The link expires in 5 minutes."
```

```tsx
t("auth.sentLinkTo", { email: sentTo })
```

### Server-side loading

`app/[lang]/dictionaries.ts` is a `server-only` module. `app/[lang]/layout.tsx` calls `getDictionary(lang)` on every request and passes the result down through `I18nProvider`.

### Client-side access

`components/i18n-context.tsx` exports three things:

| Export | Purpose |
|---|---|
| `I18nProvider` | Wraps the subtree with the loaded dictionary |
| `useT()` | Returns `t(key, vars?)` — a translation function |
| `useLocale()` | Returns the current locale string (`"en"` or `"cs"`) |

Every `"use client"` component that needs translations calls:

```tsx
const t = useT();
const locale = useLocale(); // only needed for navigation
```

### Navigation

Because routes now include the locale prefix, navigation calls use `useLocale()`:

```tsx
const locale = useLocale();
router.push(`/${locale}/explore`);
```

## Known gaps

- **`html lang` attribute** — the root `app/layout.tsx` has `lang="en"` hardcoded. The locale-specific layout cannot override it without being the root layout. To fix, delete `app/layout.tsx` and promote `app/[lang]/layout.tsx` to the root (moving the font setup there). Left as future work.
- **Magic link emails** (`lib/magic-link-email.ts`) — the email body is English only. Localising it requires threading the user's locale through the `better-auth` magic link flow so the server knows which language to use when the email is sent. Left as future work.
- **Language switcher UI** — a `LanguageSwitcher` dropdown sits in the top nav bar (between the search field and the sign-in button). It shows the active locale's badge (EN / CS / DE / FR / ES / 中文), expands on hover, and navigates to the same page in the chosen locale by swapping the locale segment in the current URL path.
- **Plural forms** — Czech plural forms are complex (1 / 2-4 / 5+). Currently a simple `_plural` suffix is used for a subset of metrics. A proper ICU-style pluralisation library (e.g. `intl-messageformat`) would handle this better for production.
